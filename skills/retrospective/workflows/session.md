# Review a session or incident

## Gather evidence

Use the visible conversation or the source the user supplied. For earlier work,
ask the installed recall skill for discovery with the already settled scope.
Return its source records here for evaluation. State missing transcript or
file-read evidence explicitly.

Look for user corrections, rejected output, repeated searches, failed paths
and improvised steps. Capture each candidate with the exact source location
or a short quotation. A file mentioned in a note is evidence of a reference;
tool records establish whether the file was opened.

## Verify and choose

Check the current file and any existing solution note before proposing a fix.
Exclude problems already fixed and ideas supported only by a vague preference.
Consider successful cases that challenge the diagnosis.

Return up to three changes. Fix a producing template first, then the owning
workflow or its index entry. Put a rule in the project instruction file only
when it applies across the project. Prefer a correction or deletion over a
new instruction layer.

## Apply and report

Show the proposed edits. Apply changes within existing authorisation; obtain
approval for any remaining write boundary. Run the checks appropriate to the
change and record their results. Skill changes can use skill-manager's
validator and review checklist. Keep validation, publication and later use as
separate states in the report.

Report the findings in chat and update the session note. Zero new evidenced
findings is a valid result. Claims about time or token savings require recorded
measurements; mark estimates as hypotheses.

## Worked example

A user corrects a generated note twice because its status field is missing.
The supplied transcript shows both corrections. The current template omits
the field, and the project schema requires it. Propose one template edit, render
one sample and check the required field. Record the correction and its check;
later sessions establish whether the mistake recurs.
